Both routes passed the same ten-column primitive/complex JDBC type-code and Java value-class comparison and a bound prepared scalar query. The SEA route returned 100,000 ordered rows with checksum `4,999,950,000` when direct results were disabled. `setQueryTimeout(1)` on SEA raised `DatabricksTimeoutException` with SQL state `STATEMENT_EXECUTION_TIMEOUT`. The initial SEA connection attempt occurred while the cluster was starting and failed with `CONNECTION_ERROR`; the retry after it reached `RUNNING` passed. The 2026-11-15 attempts in the earlier record also failed at connection open; neither failure was treated as a driver regression.

On 2026-11-18, the [round-2 route runner](validation/ApcRound2Routes.java) omitted `UseThriftClient` entirely while the live SAFE lookup returned `found=false`. The resulting connection ID identified Thrift, the session's target client was `DatabricksThriftServiceClient`, and `SELECT 1` passed. No SEA client was instantiated for that connection. The same runner set `UseThriftClient=0;EnableQueryResultDownload=0;UseBoundedSeaApi=0` and `1` in separate live connections: both identified `SEA_APC`, used `DatabricksSdkClient`, reported cloud fetch disabled in the connection context, and passed `SELECT 1`. The local CreateSession fake-service test verifies the corresponding `can_cloud_download=false` request field. These checks cover the unaffected AC8 route and session setting.

For AC27, the [round-2 wire runner](validation/ApcAc27Wire.java) intercepted the driver's SDK `HttpClient` response entity **before JSON deserialization** during a delayed, 100,000-row APC SEA query. It captured every polling GET request's method, target shape, query presence, and zero-byte body, plus the raw HTTP response entity bytes. The [sanitized payload record](apc-release-validation-ac27-wire.json) includes each raw body's byte length and SHA-256 digest and the full redacted body of every RUNNING response. **Four RUNNING polls** each returned an 84-byte JSON body containing only `statement_id` and `status.state=RUNNING`; none contained an attachment, Arrow batches, columnar data, or external links, so transferred result-payload bytes were **zero**. One terminal poll followed; the JDBC ResultSet returned all 100,000 ordered rows once with checksum `4,999,950,000`. The body length is measured at the SDK HTTP transport boundary; HTTP content encoding may already have been decoded by Apache HttpClient. The earlier post-deserialization count is retained as historical evidence, not the release measurement.
